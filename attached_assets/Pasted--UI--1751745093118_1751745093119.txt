好的，这是一个非常棒的、更具体的修行场景。它将“计时类”修行分为了两种截然不同的发愿模式。我们完全可以设计一个统一的、灵活的系统来支持这两种场景。

我将为您更新**数据库**、**UI界面**和**业务逻辑**，以清晰地实现这两个场景。

-----

### **核心设计思路**

为了区分这两种场景，我们将在总项目（`user_practice_projects`）中引入一个“目标类型”字段。

  * **场景1 (质量导向):** 我们称之为 **“法门进度”** 模式。重点是保证**每个法门**的完成质量（每周至少4座）。
  * **场景2 (时间导向):** 我们称之为 **“固定时长”** 模式。重点是在**固定时间**内完成每日的修行量。

### **一、 数据库结构更新**

1.  **`user_practice_projects` 表 (用户修行总账本):**

      * **新增** 一个字段 `goal_type`，用于区分这两种发愿模式。

    <!-- end list -->

    ```sql
    -- 更新后的 user_practice_projects 表结构
    CREATE TABLE public.user_practice_projects (
        -- ... (其他字段)
        goal_type VARCHAR(20), -- 新增字段: 'topic_progress' (法门进度) 或 'fixed_duration' (固定时长)
        target_period VARCHAR(10),
        -- ... (其他字段)
    );
    ```

2.  **`meditation_records` 表 (观修流水账):**

      * **新增** 一个字段 `notes`，用于存储用户的“观后感”。

    <!-- end list -->

    ```sql
    -- 更新后的 meditation_records 表结构
    CREATE TABLE public.meditation_records (
        -- ... (其他字段)
        duration_minutes INTEGER NOT NULL,
        notes TEXT, -- 新增字段: 观后感
        created_at TIMESTAMP
    );
    ```

3.  **`user_practice_topic_progress` 表 (法门进度清单):**

      * 这张表对于实现**场景1**至关重要，用来追踪每个法门的完成情况。

    <!-- end list -->

    ```sql
    -- (之前已提议)
    CREATE TABLE public.user_practice_topic_progress (
        id uuid NOT NULL DEFAULT gen_random_uuid(),
        user_practice_project_id uuid REFERENCES public.user_practice_projects(id),
        meditation_topic_id uuid REFERENCES public.meditation_topics(id),
        total_completed_sessions integer DEFAULT 0, -- 针对此法门的总完成座数
        status VARCHAR(20) DEFAULT 'not_started',
        UNIQUE (user_practice_project_id, meditation_topic_id)
    );
    ```

### **三、 详细技术逻辑**

#### **发愿（后端逻辑）**

  * **当用户选择场景1 (“按法门进度”) 时:**

    1.  在 `user_practice_projects` 表创建一条总项目记录，`goal_type` 设为 `'topic_progress'`，并记录每周目标座数。`target_end_date` 为 `NULL`。
    2.  **批量初始化：** 在 `user_practice_topic_progress` 表中，为全部92个法门创建对应的进度条目，`total_completed_sessions` 初始为 `0`。

  * **当用户选择场景2 (“按固定时长”) 时:**

    1.  在 `user_practice_projects` 表创建一条总项目记录，`goal_type` 设为 `'fixed_duration'`，并记录每日目标座数和 `target_end_date`。

#### **记录（后端逻辑）**

1.  在 `meditation_records` 表中插入一条新记录，包含 `duration_minutes` 和 `notes`。
2.  **如果**这个项目是**场景1**的：
      * 找到 `user_practice_topic_progress` 中对应的法门进度条目，将其 `total_completed_sessions` 字段 `+1`。
3.  **（可选）** 更新总项目的 `current_count` 字段，使其 `+1`。

#### **主页显示（前端计算逻辑）**

  * **对于场景1的卡片:**

      * **“本周已达标法门”** 的计算比较复杂：
        1.  获取当前项目关联的所有法门（92个）。
        2.  **循环**遍历这92个法门。
        3.  对于**每一个法门**，查询`meditation_records`表，计算它**在本周内**被记录了多少次。
        4.  统计有多少个法门的“本周记录次数” `>=` 用户设定的每周目标（例如4次）。这个数字就是“已达标法门”数。

  * **对于场景2的卡片:**

      * 逻辑与我们之前讨论的每日计时类完全一样。
